# fg-loop — goal-driven loop with bounded replan (outside the loop)

This is **not** a stage of the forge loop. It is a goal-driven orchestrator: one upfront conversational inquiry fixes a **machine-verifiable stop condition**, then fg-loop drives whole task loops (run → verify → auto-skip retro → seal) **until the stop-condition checks pass** — including, within explicit bounds, generating its own fix-forward tasks when checks fail. It is the third lane next to the formal loop (retro conversation included) and `fg-next all` (drain the human-grilled backlog, halt at empty): fg-loop converges on a goal instead of merely draining a queue. Rationale and the three bounds: `.forge/adr/0016-fg-loop-goal-driven-bounded-replan.md`.

**This deliberately relaxes pillar #1 within bounds** (the precedent is fg-quick relaxing pillar #2 for trivial work — ADR-0003): fg-loop may create plans without a per-plan grilling conversation, but **only** inside the replan scope the user pre-authorized during the initial inquiry, and **never** past the cap or the walls. "The AI thinks it's done" is **not** a stop condition — only the recorded checks are.

## Autonomy contract — the whole point of this lane (ADR-0016 rev. 2026-06-13)

Once the goal contract is pinned, the drive runs **unattended to completion**. It does **not** pause to ask the user for preferences or confirmations. At every *soft* decision point — one that carries a recommended or default option (a delegated skill's handoff menu, the TDD question, a slug-collision prompt, any "retro vs. skip" choice, "which task first") — **auto-select the recommended/default and proceed silently**; never turn such a choice into a question to the user. Retro is always auto-skipped (§2); where fg-run's single-task **statement-form** handoff states the skip-retro-and-seal option, the drive takes that path without prompting (ADR-0015 amended 2026-06-15 — the old four-option menu was dropped).

The drive's **only** legitimate stops are goal-met, the walls and declared external-evidence waiting in §4, and a workflow-script approval the harness physically requires to continue. **None of these human-needed walls is a "preference with a recommendation"**: each is a genuine block where proceeding alone would be *wrong*, not merely unconfirmed — a silently-sealed unverifiable UAT would violate ADR-0009; a genuine design fork is consequential and the human's to make. So "don't ask the user" and "halt at the walls" are **not** in tension — the walls are precisely the points where there is no recommendation to auto-pick.

Keep the **initial inquiry (§1) lean**: ask only what is needed to pin the machine-verifiable checks, the replan scope, and the cap. Take the documented defaults for everything else — TDD per `.forge/config.json`, the default replan scope, cap 3, auto-decompose into tasks — rather than grilling each sub-decision. The human judgment this lane preserves is *pinning the stop condition up front*, not approving each step toward it.

**One deliberate exception carves out of "lean": the *faithfulness* of the stop-condition checks themselves.** Leanness applies to the periphery — replan scope, cap, and sub-decisions (TDD, slug, task decomposition) — **never to the checks**. The checks are the *only* thing that decides "done" in an unattended drive, so a gameable or incomplete check is exactly what makes looping untrustworthy; grill the checks' faithfulness adversarially (§1's four lenses) even though that makes the check-pinning part of the inquiry non-lean. Grilling the checks hard *is* the "pinning the stop condition up front" this lane preserves, done properly — not a contradiction of leanness but its correct boundary (ADR-0016 amended 2026-07-16).

**Language**: This skill file is authored in English, but **you MUST write every message shown to the user — inquiry questions, status lines, halt reports, and handoff text — in the user's language (detect it from the user's own messages), never mirroring this file's English.** Documents it writes into the user's project (loop.md, generated plans) are written in the user's language.

**Explaining forge**: forge's vocabulary is not the user's — `verified: failed`, `unsealed tail`, a pillar or gate name means nothing unread. **Always, never gated on `eco`**: gloss a forge-specific term on first use in a message (a few words, not a paragraph), put the purpose before the mechanism, and lead with the answer, closing on what it means for the user. A gloss is not filler — with `eco` on, ECO.md's terse rules govern **form** (length, padding) while these govern **vocabulary**, so terseness never deletes a gloss.

**Host contract**: unattended driving depends on the host's `prevent_stop` capability (forge's `Stop` hook — the mechanism is defined once in [`../fg-next/DRIVE.md`](../fg-next/DRIVE.md) Part 2). Read [../../core/HOST.md](../../core/HOST.md) and check `../../hosts/<host>/capabilities.json`. When `prevent_stop` is `false` or the host is unknown, **the drive is not broken — it is turn-bounded**: it runs as far as one turn allows, keeps `loop.md`, and resumes statelessly on re-trigger (DRIVE.md's honest fallback). Say so at drive entry rather than implying continuous execution. **Every wall, gate, and cap in this file is host-neutral and unaffected.**

**Forge root**: every `.forge/...` path below is **relative to the resolved forge root** — `.forge/` on the default branch, `.forge/branch/<branch>/` (git-tracked) on any other branch. Resolve it per `${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/skills/fg-run/FORGE-ROOT.md` (skill-relative `../fg-run/FORGE-ROOT.md`) before reading or writing state (ADR-0011).

## 1. Initial inquiry (conversational — outside any workflow)

**Branch on whether the contract already exists.** If `.forge/loop.md` is present, this drive is a **resume**: skip this section entirely and go straight to §2 (its resume preflight owns validating any newly supplied decision and writing contract updates). If `.forge/loop.md` is **absent**, this is a new goal and the contract must be pinned first — **read [`INQUIRY.md`](./INQUIRY.md) and follow it.** It owns the whole conversational inquiry: settling the goal, the machine-verifiable stop-condition checks (and `evidence: external`), the approved fix-forward scope, the replan cap, the `budget-tokens` ceiling, the pre-flight check-health probe, the `## Tasks` membership list, and writing `loop.md` plus the initial backlog.

This inquiry is **conversational and outside any workflow** (pillar #1) — it is split into that file only for token efficiency on the resume path, which is the common one during a drive; **behavior is unchanged** from when it lived inline.

## 2. The drive

**Write the drive marker at entry, and delete it at every exit (ADR-0028 amended 2026-08-22).** Only after resume preflight permits driving, and only when the host's `prevent_stop` capability is `true`, write `<forge-root>/drive.md` (`started:` epoch seconds · `blocked: 0` · `session:` this session's id) — the shape and rationale are defined once in [`../fg-next/SKILL.md`](../fg-next/SKILL.md) "all mode"; do not restate them. forge's shipped **`Stop` hook** blocks the turn from ending while that marker lives, which is what lets `/fg-loop` alone drive to the stop condition without `/goal` (now a fallback). **It is a separate file on purpose: nothing is added to `loop.md`**, so this skill's discipline of absorbing new capability into existing sections rather than minting fields is untouched.

Delete the marker at **every** exit — all **nine** walls (`no-progress` · `cap-exhausted` · `unverifiable-uat` · `fork` · `tension` · `safety` · `stalled-waiting` · `blocked-health` · `budget-exhausted`), **goal-met**, and a **`waiting` turn-end**. The last one is easy to miss because `waiting` is deliberately *not* a wall (§4) — but the drive genuinely cannot proceed until external evidence lands, so a live marker there would spin the turn against something no local action can change. A workflow script approval is the same case.

Drive one task loop at a time, reusing `fg-next all`'s machinery **by reference** (`../fg-next/SKILL.md` "all mode" — do not duplicate its rules here). Select the next backlog plan **listed in `loop.md`'s `## Tasks` section**, using fg-run's priority → part → slug order among members only, then **invoke fg-run with that member's `task:` number or slug**. fg-run still owns the promotion into the active slot; the explicit identifier prevents its ordinary multi-backlog selector from offering or auto-taking a non-member plan. A backlog plan not on the list is **not** the loop's to run: leave it untouched and mention it in one status line; it belongs to the formal loop. Then execute via fg-run, attempt the UAT aggressively, **always auto-skip the retro** (recorded by the done stage as `retro: skipped (fg-loop auto-drive — learnings stay in run.md, promotion deferred to a later fg-learn)`, written in the user's language — same write-attribution as fg-next all), seal via fg-done, and continue. All per-task writes, including promotion, happen inside the delegated skills; fg-loop itself writes `loop.md`, the plans it generates, and the marker-only `repaired-by` provenance on an in-place failed repair (see §3) — this is the deliberate difference from fg-next, which writes nothing.

**Do not end the turn between task loops (within-turn continuation — [DRIVE.md](../fg-next/DRIVE.md) Part 1).** After sealing, immediately check the stop conditions and continue to a member task or bounded replan. Stop at goal-met, a wall, or a declared external-evidence wait. Cross-turn continuation and its honest host-dependent fallback are owned by DRIVE.md Part 2; a delegated handoff is not a new approval gate.

**After each seal, and whenever the backlog empties, run the stop-condition checks** and update both their checkboxes AND the **`## Check progress` ledger** in `loop.md` (each check's result, its consecutive no-progress count `×N`, its regression count `regressed: ×N` — compare each freshly-run result against the result the ledger currently records; a `pass`→`fail` flip is a **regression event**, but **increment `regressed:` only when the just-sealed work was a fix-forward** (a generated plan with `generated-by: fg-loop`, or an in-place repair carrying `repaired-by: fg-loop`) — that is the tension signal (§3). A flip caused by a **human-grilled member task** during backlog drain is normal multi-task interference, **not** tension: record it in `last-evidence` (the check is now failing, which the remaining backlog or the eventual fix-forward addresses) but do **not** count it toward `regressed:`, and do **not** halt the drain — the `last-evidence` you observed, and any `tried:` slug). This persisted ledger is what makes the no-progress wall, the tension wall, and fg-status work across a stateless resume — update it every run:

**Meter the spend at those same checkpoints — no new checkpoint is introduced (ADR-0016, amended 2026-08-19 / 2026-08-20).** fg-loop only regains control at a **task boundary** (fg-run owns the workflow, and a Dynamic Workflow takes no input mid-run), so mid-task interruption is not a reachable option.

**Be honest about what the number is when you report it.** It is the raw four-field token total over every `message.usage` in **this project's** transcripts since `since:` — i.e. **token throughput for the whole project while the loop is alive**, not this drive's billed cost. Cache reads dominate it and are far cheaper per token, and work a human does in this repo between a wall and a resume lands in the next delta. Both are accepted: this is a **safety bound, not an accounting ledger**, and over-counting is the safe direction (an early halt is raised by a human; under-counting means the ceiling never fires). Counting cache reads is the point — they *are* the context re-sent on every iteration.

**Call the meter ONCE per task boundary** — `bash "${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/forge-loop-spend.sh"`, or `node "${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/forge-loop-spend.js"` where there is no bash (dual dispatch, ADR-0022). One call yields both verdicts; there is **no `--preflight` flag**. Post-hoc and pre-flight were once two calls at what is the same moment, and the first advanced `since:`, so the second re-counted the interval and inflated the spend (measured `10` → `20`). Route by **exit code** (the script judges, this prose sets the wall — ADR-0030/0031):

- Exit `3` (`EXHAUSTED spent=N cap=M`) → the ceiling is reached. Halt with `wall: budget-exhausted` (§4).
- Exit `4` (`PREFLIGHT-HALT … avg=A remaining=R`) → the remaining budget is below the observed per-task average (spend ÷ member tasks already sealed), so the next task probably cannot be covered. Halt with `wall: budget-exhausted`. The **first task has no average and therefore always starts**, which bounds the worst-case overshoot at one task; a conservative false halt is the safe failure direction.
- Exit `5` (`BLOCKED <reason>`) → a ceiling **is** declared but cannot be measured (transcript root unreadable, `since:` not a timestamp, ceiling value unparseable). Halt with `wall: blocked-health (<reason>)` — an environment defect, not a code one (§4 #8), and **never** read as "nothing spent yet". Reporting 0 spend here is what makes a broken ceiling invisible, so the two states are deliberately distinct.
- Exit `0` (`OK …`, or `NONE no-budget-declared` when `budget-tokens: none`) → carry on.

**The meter is host-coupled, and that coupling fails closed — say so before declaring a ceiling.** What it sums is the raw token total of *Claude Code's* session and subagent transcript files (`~/.claude/projects/<slug>/`). On a host that does not write them, the derived root simply is not there, so the meter returns exit `5` (`BLOCKED transcripts-unreadable`) and the drive halts at `blocked-health` — it never reads an unreadable root as "nothing spent yet". That is the safe direction, but a halt on the first task boundary is a poor surprise, so **when the active host is not Claude Code, either declare `budget-tokens: none` (the checks are bypassed entirely) or point the meter at that host's own transcript location with `--transcripts DIR`.** There is deliberately no built-in path for another host: inventing one would be a claim about a location nobody has observed, and the capability discipline in [`../../core/HOST.md`](../../core/HOST.md) forbids exactly that.
- Exit `2`/`64` are state/usage faults, not budget verdicts — report them and do not invent a wall.

- **All checks pass** → the goal is met. Report a summary (tasks sealed, rounds used, check evidence), **delete `loop.md`**, and stop. The loop is closed.
- **Backlog still has tasks** → keep driving.
- **Backlog empty, some checks fail** → enter a replan round (§3) if bounds allow; otherwise halt at the wall.
- **Backlog empty, and the only non-passing checks are `evidence: external` ones** → this is **`waiting`, not a failure and not a wall**. **Ensure `wall:` reads `none` before ending the turn** (only after preflight has established that any earlier wall is resolved): a waiting turn-end with a leftover wall cause would present the same state as simultaneously "a wall the human must resolve" and "a wait owing the human nothing". Increment each such check's `waiting ×N` with the evidence you observed, consume **no** `replan-round`, generate **no** fix-forward, and end the turn with a report that says plainly: *nothing is owed by the human — the drive resumes on the next `fg-loop` trigger once the external evidence has landed.* Then apply the bound: if a check's `waiting ×N` reaches **2** with `last-evidence` unchanged, the wait has stalled — set `wall: stalled-waiting (Cx)` and hand it over (§4). Since no predicate can ever flip a declared-external check to "failed" (§1), **this bound is the only thing preventing an indefinite wait**, so never skip it.
- **Some checks fail AND some are waiting** → the failures win: drive the failing ones normally (replan per §3) and carry the waiting ones forward in the ledger untouched. Waiting never blocks progress on a check that *can* be worked.

**Capability precheck — before the first stop-condition run of a drive (ADR-0016, 2026-08-09).** A check whose command cannot execute at all (`gh` absent, a build tool missing, no permission) fails identically to a check whose code is wrong — so without this gate the drive reads an *environment* problem as a *code* problem, spends `replan-round` on fix-forwards that cannot possibly help, and ends at a `no-progress` wall that tells the human nothing about the real cause. Gate it **before** spending, in two layers, and ask the user for nothing (a declared capability list would violate §1's lean contract and would duplicate information the check commands already carry):

1. **Derive, don't declare.** Every stop-condition check is already "a command + an expected outcome," so take each check command's executable name(s) and confirm they resolve (`command -v <name>`). Any that do not → halt with `wall: blocked-health (<name>)` before running a single check.
2. **Conservative post-hoc promotion.** Layer 1 sees only the leading executables — it misses a tool behind a pipe, an installed-but-unauthenticated CLI, or a permission denial. So when a check fails, promote it to `blocked-health` **only** when the command demonstrably never reached the thing under test (executable-not-found, permission denied, and the like). **When it is ambiguous, treat it as an ordinary failure.** The asymmetry is deliberate: misreading an environment problem as a failure costs a wasted round (today's behavior), while misreading a real failure as an environment problem *hides a genuine bug*.

Like `waiting`, `blocked-health` consumes **no `replan-round`** and generates **no fix-forward** — there is nothing in the code to fix. Unlike `waiting`, it **is** a wall: it clears only when a human changes the environment (§4).

## 3. Bounded replan (the relaxed gate — ADR-0016)

Two situations produce fix-forward work without a human conversation, both bounded by `loop.md`, but they use different storage because the active-slot invariant must hold:

- **A task's UAT comes back `verified: failed`** — in fg-next all this is a hard wall; **in fg-loop it is the automated case**. The failed task still occupies the only active slot, so **repair the same active task in place** through fg-run's existing `verified: failed` branch (apply the bounded fix → fresh run.md → re-verify); **do not enqueue a separate backlog plan**, which fg-run could not promote while the failed slot is occupied. Before acting, **increment `replan-round` before the repair attempt**; if it now exceeds `replan-cap`, halt. Derive the repair directly from the failing check + its `tried:`/`reflection:`, record a synthetic attempt label such as `<slug>-repair-rN` in that check's `tried:` ledger, add a marker-only `<!-- repaired-by: fg-loop -->` comment to the active plan (preserve its slug/task/goal/slices), and route the proposed fix through the same authorized-scope and safety gates below. PLAN-FORMAT.md's fix-forward eval rule is **advisory** here, not binding (`../fg-run/PLAN-FORMAT.md`; ADR `260906-171420` as amended): the rule binds plans that are newly authored, while this path edits an already-run plan under a marker-only, slice-preserving contract — requiring it to add a slice would order it to break that contract. Add the regression check only if it fits inside the bounded repair; otherwise leave it to the retro's eval promotion. Never seal a `failed` result — ADR-0009 is untouched. (`/goal` does not stop at `verified: failed`, so cap/scope/safety must be checked before this in-place repair.)
- **Backlog empty + stop-condition checks failing** — increment `replan-round` in `loop.md`; if it now exceeds `replan-cap`, halt (wall). Otherwise generate new fix-forward backlog plan(s), one per failing check cluster, **strictly inside the authorized replan scope**. This path runs only with the active slot empty, so normal plan generation/promotion is valid.

**Never fix-forward a `budget-exhausted` halt, and never spend a `replan-round` on it (ADR-0016, amended 2026-08-19).** A spent budget is not a defect in the work — there is no code a fix-forward could change to make it untrue, exactly as with `waiting` and `blocked-health` below. It differs from `waiting` in that it **is** a wall: the human must decide whether the goal is worth more spend (§4).

**Never fix-forward a `waiting` or `blocked-health` check (ADR-0016, 2026-08-09).** Both paths above act only on a check that is *judged failing*. A check declared `evidence: external` that is not passing is `waiting` (§1/§2) — the drive cannot tell a red result from an unfinished one, so generating a repair would be fixing a problem it has not established exists. A check classified `blocked-health` is an environment defect, not a code defect. In both cases: no generated plan, no in-place repair, no `replan-round` spent. `waiting` ends the turn as a non-wall report; `blocked-health` halts as a wall.

**Feed Reflexion forward (ADR-0016 2026-06-18, 2nd).** Before any fix-forward attempt for a failing check, **read that check's `tried:` labels and `reflection:` from the `## Check progress` ledger first**, and make the next approach materially different — seeded by the reflection's "try differently", not a re-run of an already-tried idea. (First failure has no reflection → derive normally.) This applies both to a generated backlog plan and to the `verified: failed` in-place repair above. If the reflection concludes the real fix needs work **outside the authorized replan scope**, do not act — surface it as a **fork wall early** (§4), before burning the cap on in-scope variations that can't succeed.

**Tension wall — fix-forwards trading one check for another (ADR-0016 2026-06-25; scope corrected 2026-06-25, 2nd).** Tension is strictly a **fix-forward** phenomenon: it counts only regressions **attributable to fix-forward work** (`regressed: ×N`, which §2 increments only for `generated-by: fg-loop` plans or `repaired-by: fg-loop` in-place repairs). A regression from a human-grilled member task during backlog drain is **not** tension — it is normal multi-task interference, and the drive keeps going (the remaining backlog / eventual fix-forward addresses the now-failing check). When a fix-forward for one check regresses another: **lenient + one retry** — on the **first** fix-forward-induced regression, generate the next fix-forward with a **hard constraint to satisfy BOTH** the target check and the regressed check (fed forward alongside Reflexion, not instead of it). If it regresses **again** — the same check's `regressed: ×N` reaches `×2`, **or** two distinct checks have each been regressed by fix-forwards at least once (a ping-pong) — the checks are in genuine tension that in-scope fix-forwards can't reconcile: halt with `wall: tension (Cx↔Cy)`, report the conflicting pair and their `last-evidence`, and hand the tradeoff to the human. This fires **before** cap exhaustion, so the human reads "C1↔C2 conflict" instead of a blunt "cap-exhausted". Detection is **mechanical** (the ledger's fix-forward-attributed pass→fail flip) — unlike the safety gate below, no judgment is involved.

Every **generated backlog plan** (the active-slot-empty case) is a normal plan: PLAN-FORMAT, `forge-slug`, next monotonic `task:` number (ADR-0005), plus a `<!-- generated-by: fg-loop -->` marker so fg-status and the audit trail show its origin (fg-status renders it as a `(loop)` origin tag) — and it follows PLAN-FORMAT.md's fix-forward eval rule (persistent regression-check slice + red → green DoD when the failing check is mechanically checkable, a one-line reason when not; ADR `260906-171420`) — and **append its slug to `loop.md`'s `## Tasks` section at generation time** (membership, §1/§2). The `verified: failed` path is the explicit exception: it repairs the already-member active task, records an attempt label in the ledger, and adds only the `repaired-by: fg-loop` provenance marker, so it creates no second task/slug. Work outside the authorized scope is neither generated nor repaired — that is a wall (genuine fork), not a judgment call to make alone.

**Safety wall — in-scope but irreversible (ADR-0016 2026-06-25; made universal 2026-06-25, 2nd).** This gate is a **mandatory precondition for *every* fix-forward attempt — a generated backlog plan and a `verified: failed` in-place repair alike** (no path skips it). Even within the authorized scope, before applying the attempt, **classify its slices/actions against the `always-halt action classes`** in `loop.md`'s Authorized replan scope (§1 — the default 7-class set, override/extend per loop). If any would take such an action — prod data mutation/deletion · deploy/release/publish · outbound external comms · irreversible VCS/file destruction · financial/payment · secret/permission change · privacy-data exposure — do **not** auto-generate or repair: halt with `wall: safety (<class>)` and hand the one-way door to the human. This is distinct from the fork wall: out-of-scope work is a fork, but an **in-scope yet destructive** action still halts (the gap the harness permission gate misses under broad permissions). **Honest limit**: this is a **best-effort self-classification** by the model, not a guaranteed interception (a Markdown plugin has no static analyzer to enforce it) — its value is that the halt is named in the contract and the `/goal` stop-allowed set, so the drive has an explicit instruction to stop rather than none.

**No-progress early abort:** use the persisted `## Check progress` count (`×N ≥ 2`) under §1's rule: consecutive failing observations with unchanged evidence, including explicit rechecks across resumes. A skipped preflight check is not an observation. This count is not the number of repairs: report `tried:` separately and never claim two attempted fixes when none ran. At the threshold, halt automatic repair and report the evidence, attempts, and any reflection. If an unresolved fork or safety decision already blocks the same check, retain that actionable wall cause while reporting the updated no-progress count; changing its label does not resolve it.

**Resolution permits one new attempt, not a counter reset.** If an explicit scope or approach decision enables a concrete repair not previously attempted, record that decision and proposed approach in the existing ledger and permit that single bounded attempt despite a retained `×N ≥ 2`. This includes a first repair previously blocked by a fork when `tried:` is empty. Apply all other gates normally. Record consumption of the decision with the attempt's `tried:` label before executing it, so a later resume cannot reuse it. If verification leaves the evidence unchanged, increment the count and halt at no-progress; a repeated "continue" does not authorize another attempt. Evidence changes use §1's normal counter update rule.

## 4. Walls and termination

Halt the drive, report where/why/how-to-resume (in the user's language), at any of:

1. **Unverifiable UAT** — a check or task verification can't reach a sealable value (`pending`); never seal unverified (ADR-0009).
2. **Genuine design fork** — including a needed fix that exceeds the authorized replan scope. Consequential branches are the human's.
3. **Replan cap exhausted** (`replan-round` > `replan-cap`).
4. **No progress** — same check failing twice consecutively with no change.
5. **Tension** (§3) — fix-forwards keep trading one stop-condition check for another (a previously-passing check regresses, then regresses again after a satisfy-both retry, or two checks ping-pong). The checks conflict; the human decides the tradeoff. Fires before cap exhaustion.
6. **Safety** (§3) — a fix-forward would require an `always-halt action class` (irreversible/destructive/external; §1). Hand the one-way door to the human. Best-effort self-classification, not a guaranteed gate.
7. **Stalled waiting** (§1/§2) — an `evidence: external` check has been `waiting ×2` with unchanged evidence. The external evidence is not arriving; the human decides whether to wait longer, fix the upstream, or drop the check.
8. **Blocked health** (§2) — a check command cannot execute (missing tool, missing auth/permission). The human fixes the environment; no amount of code change helps.
9. **Budget exhausted** (§2) — the declared `budget-tokens` ceiling is reached (post-hoc) or the remaining budget is below the observed per-task average (pre-flight). Consumes **no** `replan-round` and generates **no** fix-forward (§3): nothing in the code is wrong, the drive simply ran out of the resource it was authorized to spend. **Its clear semantics differ from every other wall and must not be "simplified":** resume preflight retains the wall until an authorized ceiling increase permits another checkpoint; a bare re-trigger neither resets the wall nor reruns the same exhausted-budget path. The only exit is the human **raising `budget-tokens`** — and `budget-spent` is **not** reset, exactly as `cap-exhausted` is resolved by raising `replan-cap` while `replan-round` keeps its count. Resetting the accumulator instead would silently discard the drive's cumulative total, which is the one number the ceiling exists to bound.
10. **Unknown or uncollectable in-flight marker (fg-run 4a case 3)** — `running.md` belongs to the active task, but the host's blocking-collect cannot identify or collect one or more recorded handles; this includes `workflow: pending`, an unavailable same-session handle, a collection error, and work that may still be running in another session. The drive cannot answer fg-run's required confirmation for the human. Set `wall: fork (unknown or uncollectable in-flight execution)`, delete `drive.md`, and stop.

**`waiting` is NOT in this list, and that is the point.** A check merely waiting on external evidence asks **nothing** of the human — no judgment, no action — so reporting it as a wall would recreate exactly the misclassification this state was added to remove (§2). It ends the turn as a non-wall report with `wall:` at `none` (§2 — never a leftover cause from an earlier halt), and resumes on the next trigger. It becomes a wall only by stalling (#7 above). Walls #7 and #8 are, like tension and safety, **fg-loop-exclusive** — they arise from the `evidence: external` declaration and the capability precheck, neither of which exists in `fg-next all`, so its wall set is unchanged.

**Wall #9 is fg-loop-only for a DIFFERENT reason, and the difference matters (ADR-0016, amended 2026-08-19).** Tension, safety, `stalled-waiting`, and `blocked-health` cannot *occur* in `fg-next all` — it generates no fix-forwards and makes no external/capability declarations. A budget overrun **can** occur there: it drives unattended and burns the same workflows. `budget-exhausted` is confined here only because the ceiling lives in `loop.md` and `fg-next all` has no contract file to hold one. That is a **scope decision, not a structural impossibility** — do not cite the sentence above as though it covered this case. The identical exposure remains in `fg-next all`, deliberately, as separate follow-up work.

On a wall, **set `loop.md`'s `wall:` field to the precise cause, then delete `drive.md` before stopping** — persisting the reason before releasing the Stop hook avoids an unrecorded-wall crash window. `fork (<reason>)` also carries a **refused per-task commit**, e.g. `fork (commit rejected — pre-commit hook)`, when `driveCommit` is on ([`../fg-next/DRIVE.md`](../fg-next/DRIVE.md) Part 3), and an unknown or uncollectable `running.md`, e.g. `fork (unknown or uncollectable in-flight execution)`; no separate wall token is minted for either — (`no-progress (C1)` / `cap-exhausted` / `unverifiable-uat (C2)` / `fork (<reason>)` / `tension (Cx↔Cy)` / `safety (<class>)` / `stalled-waiting (C2)` / `blocked-health (<capability>)` / `budget-exhausted`) so fg-status and the resume report *why* it stopped — never a bare "resume fg-loop". `loop.md` stays on disk (fg-status reports it); the human resolves the wall — possibly re-grilling via fg-ask or widening the scope/cap by editing the inquiry's answers in a short conversation — then fg-loop records that decision and resumes in the same conversation; a later invocation uses the resume preflight rather than treating the trigger as resolution. On goal-met termination, `loop.md` is deleted and a final summary is the handoff (statement form — point to fg-learn for a later batch promotion of the archived run.md learnings, per ADR-0010's deferred-promotion model).


### Unattended across turn boundaries — pairing with `/goal`

Cross-turn continuation and its conditional `/goal` fallback are defined in [DRIVE.md](../fg-next/DRIVE.md) Part 2. Use the fallback only at runnable drive entry as specified in §1. **Enumerate the stop-allowed points from THIS loop's walls, not fg-next's**: goal-met (all checks pass) · unverifiable UAT (`pending`) · genuine fork / out-of-scope fix · an unknown or uncollectable `running.md` (fg-run 4a case 3) · replan cap exhausted · no progress ×2 · tension (regression ping-pong) · safety (irreversible action class) · stalled waiting ×2 · blocked health (a check command cannot execute, or a declared ceiling cannot be measured) · **budget exhausted** (the `budget-tokens` ceiling is reached, or the pre-flight estimate cannot cover another task) · a workflow script approval (human input is physically required). **Also list plain `waiting` as a stop point** even though it is not a wall — the drive genuinely cannot proceed until external evidence lands, so a `/goal` that refused to stop there would spin. Do **not** list `verified: failed` as a stop point — in fg-loop it is the automated fix-forward case (§3), and a `/goal` that halts on it would undo exactly the wall-relaxation this skill exists for. Recommended paste-ready shape (render in the user's language):

> *"Keep driving fg-loop. Stopping is allowed only at: (1) goal-met — every stop-condition check passes; (2) a wall — unverifiable UAT, a genuine fork or out-of-scope fix, an unknown or uncollectable in-flight execution, replan cap exhausted, no progress ×2, tension (checks ping-pong), a safety/irreversible action, stalled waiting ×2, budget exhausted, or a check command that cannot execute (blocked health); (3) waiting on external evidence that has not arrived; or (4) a workflow script approval. On `verified: failed`, do not stop — continue with fix-forward."*

### Relationship to the other lanes

- **`fg-next all`** drains the human-grilled backlog and halts at empty state and at `verified: failed`; it never creates work. fg-loop is the goal-converging superset: it re-checks a goal at empty state and may generate bounded fix-forward work, and `failed` is its automated case. **The tension and safety walls (§3/§4) are fg-loop-exclusive** — both arise only from *generated* fix-forwards, which fg-next all never produces, so they do not ripple into fg-next's wall set (the two lanes share only the `/goal` mechanism, not this wall pair).
- **The formal loop / one-shot `fg-next`** keep the retro conversation; fg-loop always auto-skips retros (learnings preserved in archived run.md, promoted later by a human fg-learn). The optional adversarial review (`fg-adversarial-review`, ADR-0018) is likewise **never** run in the drive — it needs a human to judge which findings are real and worth fixing.

**Where this sits in "loop engineering" terms (maker/checker · deployment levels).** This lane *is* the "recursive goal" of loop engineering — define a purpose; the AI iterates with sub-agents, verification, and external state until the goal is met or it hands off to you — pinned **stricter**: "the AI thinks it's done" is never a stop condition here, only the recorded machine-verifiable checks. The maker/checker split maps cleanly: fg-run's workflow sub-agents are the *maker*; the per-task UAT is a self-administered *checker*, **but the machine-verifiable stop-condition checks are the independent, objective checker** — a `grep`/test/build outcome is not subject to maker bias, so an over-optimistic UAT is caught when a stop check still fails and triggers a fix-forward (§3). That is why **no separate verifier sub-agent runs in the drive**: the mechanical checks already gate, and a redundant verifier would add complexity without closing a real hole. The three forge lanes are the L1→L2→L3 rollout (report → assisted → unattended) — fg-status (L1, observe) · fg-next (L2, assisted) · fg-loop / fg-next all (L3, unattended) — and `loop.md`'s Check-progress ledger + Reflexion is the durable memory/state spine that survives a stateless resume.

## Handoff

**During the drive, no delegated table reaches the user — fg-loop suppresses it.** fg-run/fg-done cannot detect their caller, so **instruct every step you invoke not to render its handoff table**; fg-loop renders exactly one, here, for its own terminal step (the wall, or goal-met). This is the same active suppression the drive already applies to the delegated seal summary ([DRIVE.md](../fg-next/DRIVE.md) Part 1, ADR-0032), for the same reason: relaying `Next step: fg-learn` while the drive auto-skips the retro *is* the "keeps telling me to run fg-learn, never seals" stall, and a table reads as an instruction, so relaying one is worse than relaying the prose was.

The terminal report **is** the handoff, rendered as the **handoff table** per [`../fg-next/HANDOFF.md`](../fg-next/HANDOFF.md) — the single definition of its shape; never restate that layout here. Statement form — no "shall I continue?" (ADR-0015).

Fill it from `loop.md`, never from memory:

- **Goal met** → `Just did` = tasks sealed · rounds used · all checks passing (the per-check evidence itself is list-shaped and goes **below** the table — see below); `Next step` = `fg-learn` as the later batch-promotion path for the auto-skipped retros; `How to start` = its trigger. State that `loop.md` was **deleted** (the loop is closed) as part of `Just did`.
- **Wall** → `Just did` = the precise saved wall and round N/cap; `Next step` = the concrete decision or evidence still missing; `How to start` = supply that decision/evidence in this conversation (name it, not a bare `/forge:fg-loop`); `Alternative` = fg-ask only when the goal/checks need redesign. If a decision is already unambiguous, apply the resume preflight and continue instead of emitting another handoff. Do not offer baseline exceptions as equivalent to preserving the original checks: changing a check requires an explicit, faithful goal decision and never waives failed task verification.

The evidence is list-shaped, so it goes **below** the table as bullets (HANDOFF.md, "List-shaped content goes below the table", which names fg-loop for exactly this). **Both termini emit it** — which lines depends on the terminus:

- **Wall** → one line per **failing** check with its `×N`, `regressed: ×N`, `last-evidence`, and `reflection:`, plus the `tried:` slugs. That detail is why the wall happened — it must not be compressed into a cell, and it must not be dropped.
- **Waiting (non-wall turn end)** → the table's `Just did` says the drive is waiting on external evidence and **that nothing is owed by the human**; `Next step` is re-triggering `fg-loop` once the evidence has landed; `How to start` = `/forge:fg-loop`. Below it, one line per waiting check with its `waiting ×N` and `last-evidence`. Do **not** phrase this as a wall or as a problem to resolve — that misclassification is what §2's `waiting` state exists to remove.
- **Budget exhausted (a wall with NO failing check)** → the material is the ledger, not the checks: `budget-spent` · `budget-tokens` · the pre-flight `avg`/`remaining` when that was the trigger, plus how many member tasks were sealed for that spend. Say plainly that **no check is broken** and nothing needs fixing — the drive spent its authorized budget — so the decision is whether the goal is worth raising `budget-tokens` for. Do **not** render failing-check lines here; there may be none.
- **Goal met** → one line per check with its `last-evidence` — the command output actually observed, which the ledger records for **passing** checks too (§1). Read it out of `loop.md` and render it **before** deleting the file (§2's goal-met order is report, then delete): the deletion destroys the ledger, so evidence never shown is evidence no longer recoverable, and an unverifiable "done" is precisely what this lane forbids — only the recorded machine-verifiable checks may stop it, never "the AI thinks it's done" (ADR-0016).

## Document impact

- Creates/updates/deletes `.forge/loop.md` — the goal contract (volatile, owned by fg-loop; deleted on goal-met termination, kept on a wall **and on a waiting turn-end**). The `waiting ×N` state and the optional `evidence: external` declaration live **inside existing sections** (the check list and the Check-progress ledger) — no new top-level field was added. The spend ceiling **did** add two top-level fields, `budget-tokens` and `budget-spent · since:`, because spend is a drive-level quantity with no per-check home (§1) — `budget-spent`/`since` are written by the `forge-loop-spend` twin, not by this prose.
- Creates `.forge/backlog/*.md` plans — at the initial inquiry and as `<!-- generated-by: fg-loop -->` fix-forward plans during the active-slot-empty replan case.
- On an in-place `verified: failed` repair, adds only `<!-- repaired-by: fg-loop -->` to the active plan for provenance/tension attribution; it preserves the plan's slug, task number, goal, and slices.
- Everything else (plan promotion, run.md, STATUS, seal, done/ archive) happens **inside the delegated skills** (fg-run/fg-done), under their own rules — including the `retro: skipped` record written by the done stage.
