# fg-run — "Run all" execute-only batch (reference)

> Split out of `fg-run/SKILL.md` for **token efficiency (progressive disclosure)**: the Run-all procedure is only needed when the user picks **"Run all"** from the 2+-task selection menu, which is the rare path. So fg-run loads this on demand instead of on every invocation — keeping the common path (one task, or a single pick) lighter. **When the user picks "Run all," read this file and follow it.** Behavior matched the original inline `SKILL.md` text at split time; the batch handoff (step 4) was since amended to statement form (ADR-0015, amended 2026-06-11).

If you pick "Run all" from the selection menu, the backlog's unfinished plans are **executed only, in sequence**. Sealing — and the retro fg-done decides inside it (ADR `261024-191024`) — is not auto-inserted: an interactive seal is where a human answers the one promotion question, so Run all stops before it and parks each task in `executed/`. Run all is not unattended automation; it is a declaration of "I'll do the execute stage in one batch." (For the superset that also drives verify → seal (with fg-done's unattended retro judgment) → promote-next until the backlog is empty — halting only at the conversational walls — see `fg-next all`, the momentum mode in `../fg-next/SKILL.md` / ADR-0010.)

1. **Confirm the order.** Snapshot and freeze the current N unfinished candidates, and show the user the execution order once (default: **priority order** — `high → medium → low`, no marker = `medium`, ties by slug alphabetical, same as the selection menu) — "shall I run them in this order? If there are dependencies between tasks, reorder now."
2. **Per-task sequential execution.** For each task i: promote `backlog/<slug>.md` → `.forge/plan.md` → run the main body of `SKILL.md` exactly once (build the workflow → approve → cross-verify → record `run.md` → write **`.forge/STATUS.md` (the active slot)** at `status: executed` → **UAT-verify the result against the plan's goal and record the outcome in `verified:`**, see "Verify before handing off (UAT)") → **branch on the UAT outcome**. **STATUS location is single and state-dependent**: during execution+UAT it always lives in the active slot (`.forge/STATUS.md`); it moves to `executed/` only on a sealable outcome.
   - **sealable (`yes`/`skipped`/`n/a`)** → without sealing, **move plan+run+STATUS together from the active slot into `.forge/executed/<slug>/` (park)** → the active slot is now empty so the next task can be promoted. **Simple mode exception (ADR `260905-212045`):** when `simple` is `true` in the **top-level** `.forge/config.json`, do not park — seal the task right there through fg-done as an **unattended** seal (its retro judgment skips the retro or writes an auto retro log, no promotion question; a delegated seal, terse — ADR-0032), which empties the active slot the same way. The `failed` branch below is unchanged either way (ADR-0009).
   - **`failed`** → **do not park, and do not create an `executed/<slug>` entry.** Leave plan+run+STATUS in the **active slot** (STATUS is already there from the execution step, carrying `verified: failed`) and stop the batch (step 3), so fg-run's §4 re-entry reliably sees the active-slot `verified: failed` and routes to fix-and-re-run or re-grill. Parking a `failed` task would strand it — fg-done blocks `failed`, and an empty active slot puts it out of fg-run's reach.
   - **Verification is part of finishing execute — it is not deferred like the seal.** Run all defers only the seal and the retro decided in it; but each task is UAT-verified before it parks, so a parked task never carries `verified: pending` or `failed` — only sealable outcomes get parked. For a docs-only task the outcome is `n/a (<reason>)`, which is quick and does not stall the batch.
   - `executed/` is the explicit expression of the intermediate state "executed but not yet sealed." Putting a task into `done/` any way other than through fg-done would skip its retro judgment and seal gates, so never send it to `done/` directly.
   - Each task gets its own run. Do not merge several tasks into one run.
3. **Failure/abort.** If task i fails, stop there — the i-1 already parked remain awaiting the seal, and i's plan/run stay in the active slot so the next fg-run's re-run guard catches them. The not-yet-started ones stay in the backlog and reappear in the next menu. Partial progress is reflected honestly in the file state. **A `verified: failed` UAT counts as a failure here** (per step 2's branch): i stays in the active slot — not `executed/` — so fg-run's §4 re-entry can route it to fix-and-re-run or re-grill.
4. **Handoff — render the handoff table.** When the batch ends, **state and stop** (statement form — ADR-0015 amended; do not ask "shall we seal now?" or "which first?") and render the batch handoff as the **handoff table**, whose shape is defined once in [`../fg-next/HANDOFF.md`](../fg-next/HANDOFF.md) — reference it, never restate the layout. Render it in the user's language.
   - **Run all is execute-only and is NOT an unattended drive**, so HANDOFF.md's "Unattended drives — the delegated skill renders NO table" section does **not** apply here: this is a human-facing batch end and it *does* render a table. Do not conflate it with `fg-next all`, which drives through the seal and owns the report itself — Run all halts before the seal by design, parking each task in `executed/`.
   - **Material.** `Just did`: N tasks ran and were UAT-verified, each parked in `.forge/executed/` with plan+run+STATUS (`status: executed`, `verified:` recorded), awaiting the seal. `Next step`: the seal — `fg-done`, which decides each task's retro (`fg-done all` seals them all as unattended seals). `How to start`: `/forge:fg-done`, or `fg-next`.
   - **A `verified: failed` task owns the cells instead.** Per step 2's branch it is *not* parked — it stays in the **active slot**, so `Next step` is fix-and-re-run with `fg-run` (trigger `/forge:fg-run`; §4 re-entry sees the active-slot `verified: failed` and routes it), with sealing the parked tasks as the `Alternative`.
   - **Per-task results go below the table as bullets** (HANDOFF.md's list rule — a list does not fit a cell, and paths are verbatim-preserved): one line per task with its `verified:` value and where it landed, plus the not-yet-started tasks still waiting in the backlog.
   - **"Which task first?" is fg-done's own question** — it selects one parked task first when several await (single definition); do not duplicate it here.
   - **Eco: report the batch as a one-row-per-task table.** If `eco` is `true` in the **top-level** `.forge/config.json`, **replace** the `Just did` material and the per-task bullets with the batch shape of the **eco summary table** — one row per task — defined once in [`../fg-config/ECO.md`](../fg-config/ECO.md); reference it, do not restate the layout. Every fact above must survive: each task's `verified:` value, that it still awaits the seal, where it parked, and the tasks set aside. The handoff table still follows it — how the two combine is HANDOFF.md's "Interaction with eco" (follow it; do not restate it here), which keeps the next step in the same place in both modes. It stays **statement form** and still does not ask "which first?". One row is shorter than the prose it replaces, which is why this serves the batch's momentum rather than fighting it (ADR-0032's 2026-07-31 amendment). When `eco` is `false` or absent, the material above fills the table unchanged.
