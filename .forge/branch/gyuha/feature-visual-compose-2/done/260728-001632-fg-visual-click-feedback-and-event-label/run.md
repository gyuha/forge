## 계획대로 된 것

- **S1** — `helper.js`에 `choiceLabel()`을 추가하고 클릭 핸들러의 `text` 필드에 적용했다. 계획대로 `.card-body h3` / `.content h3`를 먼저 찾고, 없으면 아무 `h3`, 그래도 없으면 전체 텍스트로 폴백한 뒤 공백을 정규화하고 120자로 잘랐다.
- **S2** — 같은 파일에 `showClickHint()`를 추가했다. 계획대로 자체 스타일(프레임 CSS 변수 미사용), 우측 하단 고정, `Selected: <라벨>` + 안내 두 줄, 자동 소멸 없음, 새 클릭 시 라벨만 갱신, 다중선택 해제 시 `Deselected:`. 라벨은 화면 콘텐츠에서 오므로 `innerHTML`이 아니라 `textContent`로 넣었다.
- **S3** — 파일 헤더 주석의 `forge modifications:` 목록을 갱신하고 `helper.js`만 커밋했다 (`f28a9e1`). forge 상태 파일은 커밋 경로에서 제외했다.

## 계획과 달랐던 것

- **워크플로우를 쓰지 않고 직접 실행했다.** task 1과 같은 판단 — 한 파일에 함수 2개를 추가하고 핸들러 5줄을 고치는 작업이라 서브에이전트를 띄우는 비용이 작업보다 크다.
- **계획에 없던 검증 두 가지를 추가했다.** 다중선택 해제 경로(`Deselected:` 전환)와 3초 경과 후 토스트 잔존 여부. 완료 기준에는 없었지만 구현한 동작이라 확인했고, 둘 다 통과했다. 기준을 넓힌 것이라 판정에는 영향 없다.

## 중간에 내린 결정

- **`showClickHint`가 매번 DOM을 새로 만들지 않고 기존 노드를 재사용하도록 했다.** 계획에는 "새 클릭 시 라벨 갱신"만 적혀 있었는데, 구현 방식이 명시돼 있지 않았다. 노드를 재생성하면 클릭할 때마다 토스트가 쌓일 수 있어 `getElementById`로 찾아 텍스트만 바꾸게 했다. 계측에서 `hintCount: 1`로 확인했다.
- **`WebSocket` 스텁을 써서 검증했다.** 서버 없이 headless Chrome에서 클릭을 시뮬레이션하려면 helper가 보내는 이벤트를 가로채야 했다. 전역 `WebSocket`을 수집용 스텁으로 갈아끼워 `send()` 페이로드를 읽었다. 리포에는 남기지 않았다(계획의 "테스트 파일 미추가").

## 검증 증거

수정된 실제 `helper.js`를 두 종류 화면에 로드해 클릭을 시뮬레이션하고 계측했다.

**라벨(S1)** — 프레임 화면(카드 3개 목업)과 전체 문서 화면(프레임 CSS 없음) 양쪽:

| 화면 | 클릭 | `text` | 길이 | 개행 |
| --- | --- | --- | --- | --- |
| 프레임 | a / b / c | `A · 좁은 중앙 모달 (권장)` 등 | 17자 | 없음 |
| 전체 문서 | a / b / c | `A · 전체 문서 카드` 등 | 7–12자 | 없음 |

수정 전 같은 클릭의 `text`는 카드 전체 텍스트 수백 자였고, 클릭 35번에 events 파일이 26KB였다.

**토스트(S2)**:

| 항목 | 프레임 화면 | 전체 문서 화면 |
| --- | --- | --- |
| 표시 | ✓ (`position: fixed`, `z-index: 99998`) | ✓ (동일) |
| 재클릭 시 라벨 갱신 | ✓ (`C…` → `A…`) | ✓ |
| 노드 중복 생성 | 없음 (`hintCount: 1`) | 없음 |
| 3초 후 잔존 | ✓ | — |
| 다중선택 해제 | `Selected:` → `Deselected:` 전환 확인 | — |

스크린샷으로 실제 렌더링도 확인했다 — 우측 하단에 어두운 카드로 `Selected: A · 좁은 중앙 모달 (권장)` + `Tell your agent in the terminal — clicks alone don't reach it.`가 표시되고, task 1의 카드 목업 수정도 함께 정상 동작한다.
