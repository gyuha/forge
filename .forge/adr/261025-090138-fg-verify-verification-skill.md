# 검증 스킬은 `fg-verify` 명령으로 만들고, UAT가 자동으로 쓴다

pstack(Lauren Tan, MIT — `cursor/plugins`의 `pstack/skills/create-verification-skill`·`maintain-verification-skill`)은 프로젝트마다 앱을 사용자처럼 띄우고 조작해 동작을 증명하는 프로젝트 전용 **검증 스킬**(`verify-<app>`: Launch·Doctor·Drive·Evidence·Cleanup + 기능 지도)을 생성하고 유지한다. forge의 UAT는 지금 "확인할 것을 보여주고 사람에게 묻는" 방식이라(`skills/fg-run/SKILL.md` "Verify before handing off"), UI·CLI 작업은 사람이 눌러 보기 전까지 `verified: yes`의 증거가 없고 무인 주행은 그 지점에서 "검증 불가 UAT" 벽에 멈춘다. 이것을 forge에 들인다.

## 결정

- **생성·갱신은 새 명령 `fg-verify` 하나** — 없으면 생성, 있으면 갱신(원본의 두 스킬을 fg-map의 "없으면 생성, 있으면 Update" 선례대로 합친다). 사람이 명시적으로 부르며 무인 주행(fg-next all·fg-loop)에선 항상 skip.
- **사용은 자동** — fg-ask가 계획 DoD에 구동할 기능 지도 항목을 지목하고, fg-run UAT가 `verify-*` 스킬이 있으면 그 항목을 구동해 증거를 남긴다. 무인 주행의 기존 "UAT는 적극적으로 시도" 조항(`skills/fg-next/ALL-MODE.md`)이 그대로 혜택을 받으므로 주행 규칙은 바꾸지 않는다. 기능의 사용자 경로를 바꾸는 계획은 그 기능 파일 수정 슬라이스를 함께 담는다. 스킬이 없고 DoD에 수동 확인 항목이 생기면 fg-ask가 한 번 `fg-verify`를 제안한다(재시작 필요를 함께 밝힘).
- **생성물 위치** — 실체는 `.claude/skills/verify-<app>/` 한 벌(Claude Code·opencode가 읽음), Codex용으로 `.codex/skills/verify-<app>` 심볼릭 링크(이 리포의 `issue-triage` 선례). 프로젝트 자산으로 git 커밋. Pi는 프로젝트 스킬 경로 미확인이라 범위 밖.
- **증거 위치** — 최상위 `.forge/verify/<slug>/`, 자체-ignore(`.forge/verify/.gitignore`에 `*` 한 줄 — fg-showme 선례)로 git 진입 경로를 구조적으로 막는다. 브랜치와 무관한 전역 예외. 자동 삭제 없음.
- **원본은 개념 각색** — forge 문서로 새로 쓰고 MIT 출처를 표기한다. 기능 지도 형식 예시(`references/feature-map-example/` 3파일)만 원형 그대로 들여와 형식의 단일 정의로 쓴다.

## 고려한 대안

- **완전 자동(fg-run이 UAT 시점에 직접 생성)** — 거부: 앱 기동·의존성 설치·빌드 수리라는 계획 밖 부작용, 프로젝트 단위 일회성 셋업, 인증 등 사람에게 물을 수 있음(기둥 1), 생성한 스킬은 세션 재시작 전까지 로드되지 않음(ADR-0024 실측) — 넷 다 실행 중 자동화와 맞지 않는다.
- **UAT가 구동할 기능을 실행 시점에 fg-run이 고름 / 매번 지도 전체 구동** — 거부: 앞은 원본이 경고한 "편한 진입점 하나만 구동"을 실행자에게 열고, 뒤는 비용이 기능 수에 비례하고 무관한 실패가 작업을 막는다. 무엇을 증명할지는 실행 전에 사람과 합의한다.
- **지도 갱신을 fg-done 봉인 때 제안 / `fg-verify` 재실행에만 맡김** — 거부: 어떤 변경이 사용자 경로를 바꿨는지 기계로 판정할 수 없어 잡음이 되거나, 사람이 잊는 순간 지도가 조용히 낡는다. 기능을 바꾸는 작업이 지도도 고치는 것이 테스트와 같은 원리다.
- **원문 vendoring + forge 덮어쓰기 절(fg-security·fg-debug 방식)** — 거부: 원문에 `.cursor/skills/` 경로·두 명령 분리·"PR 하나로 출시"가 박혀 있어 위 결정 셋과 정면 충돌한다. 덮어쓰기 구조는 fg-ask에서 이미 알려진 드리프트 위험이다. 앞의 두 vendoring은 원본 경로가 일반적이어서 충돌이 없었다.
- **증거를 리포 밖에 둠(fg-security 방식)** — 거부: 커밋 경로가 없는 것은 같지만 UAT 증거를 리뷰·회고가 찾아가기 어렵다. 대가로 전역 예외가 하나 늘어 CLAUDE.md·`FORGE-ROOT.md`·상태 계약 문서가 함께 바뀐다.

## 결과

- 스킬이 25개가 되고 핸드오프 적용 지점이 16곳이 된다(카탈로그·README 쌍·docs 쌍·Pi 테스트의 개수 단언 동기 필요).
- 이 리포에는 구동할 앱이 없어 forge 안에서 실제 생성·UAT 연동을 끝까지 dogfood할 수 없다. 실동작 검증은 다른 프로젝트에서 따로 해야 한다.
- 낡은 지도는 UAT `failed`로 드러나며, 지도 탓으로 추정해 통과시키지 않는다(경로를 약하게 고치지 않는다).

## 개정 2026-10-26 — 봉인 전 코드 리뷰 반영

봉인 전 `/code-review`가 위 결정의 빈틈 넷을 잡아 계약을 고쳤다.

- **재시작 요구 철회** — 루프는 `verify-<app>`을 스킬로 호출하지 않고 **파일을 읽어 따른다**(`fg-verify` 자신의 증명 실행과 같은 방식). 그래서 만든 세션에서 바로 쓸 수 있다. 원래 fg-run에 적었던 "재시작 전이면 종전 UAT로" 분기는 판별 수단이 없었다(디렉터리 존재만 보이고 재시작 여부는 보이지 않는다). 위 "고려한 대안"의 첫 거부 사유 넷 중 "재시작 전까지 로드되지 않음"은 이제 루프에는 해당하지 않는다. 나머지 셋(계획 밖 부작용·일회성 셋업·사람에게 물을 수 있음)만으로 완전 자동 생성을 거부하기에 충분하다.
- **실패와 차단 구분** — UAT 판정을 "어디서 멈췄나"로 가른다. Launch·Doctor를 통과하지 못했으면 작업에 대해 알아낸 것이 없으므로 `failed`가 아니라 `verified: pending`(무인 주행에선 기존 "검증 불가 UAT" 벽)이다. Doctor 통과 뒤 결과 상태가 기능 파일과 다를 때만 `failed`다. 이전 문언은 인증 만료 같은 환경 문제도 `failed`로 기록해, fg-loop의 제자리 수리가 멀쩡한 코드를 상한까지 고치게 만들 수 있었다.
- **무인 주행의 구동 범위** — 무인 주행이 금지되는 것은 검증 스킬의 *생성*(의존성 설치·빌드 수리·인증 질문)이지, 사람이 그릴링에서 지목한 journey의 *구동*이 아니다. 단 Doctor가 사람을 요구하거나 journey의 부작용이 그 실행이 띄운 인스턴스 밖으로 나가면(실제 메시지·결제·공유/운영 시스템) 무인 주행은 구동하지 않고 `pending`으로 멈춘다. 무인 수리는 기능 파일을 고쳐 journey를 통과시키지 않는다.
- **증거 레이아웃** — 시도마다 새 디렉터리 `.forge/verify/<run>/<YYMMDD-HHMMSS>/`를 쓴다. 고정된 `<slug>/` 하나는 fix-and-re-run 라운드끼리, 그리고 같은 slug를 쓰는 브랜치끼리 증거가 섞였다. 레이아웃과 자체-ignore 규칙은 `skills/fg-run/FORGE-ROOT.md`의 `.forge/verify/` 항목 하나에만 정의하고 다른 곳은 참조만 한다.
- **다중 표면** — 검증 스킬이 이미 있으면 기존 것을 갱신할지, 다른 표면용으로 새로 만들지 묻는다(이전에는 무조건 갱신으로 갔다).
- **예시의 `artifacts/` 경로** — 원형을 보존한 기능 지도 예시는 *형태*만 정의한다. 예시 속 리포 상대 경로 `artifacts/…`는 업스트림의 예시일 뿐이며, 생성되는 지도는 증거를 `.forge/verify/`에 쓴다(`artifacts/`는 `git add -A`에 스테이징된다).
