# fg-merge에 feature 브랜치에서 실행하는 `to <대상>` 모드를 둔다 — 이 모드만 커밋한다

## 맥락
작업을 끝낸 feature 브랜치에서 "현재 브랜치를 커밋하고 main으로 머지"하려 했지만 fg-merge는 그렇게 동작하지 않았다. 기존 두 모드(`fg-merge` 통합만, `fg-merge <branch>` 끌어오기)는 **기본 브랜치에 서서 다른 브랜치를 끌어오는** 방향이고, 다른 브랜치에서 실행하면 멈추며, 통합 결과를 커밋하지 않는다(ADR `260717-10a`). 사용자가 손으로 하던 순서(커밋 → checkout → merge → 통합 → 커밋)가 한 명령으로 묶이지 않았다.

## 결정
**`fg-merge to <대상>`을 세 번째 모드로 추가한다.** feature 브랜치에서 실행하고, `to` 키워드로 방향을 못 박는다. 흐름은 다음과 같다: 게이트 사전 검사 → 확인 1회 → (1) 미커밋 변경 커밋 → (2) 대상 checkout → (3) `git merge <feature>` → (4) 결정론 스크립트로 forge 기록 통합 → (5) 통합 결과 커밋.

- **대상은 기본 브랜치만.** forge 통합의 목적지가 최상위 `.forge/`이기 때문이다. 대상을 생략하면 기본 브랜치로 본다.
- **게이트를 1단계 앞으로 당긴다.** 스크립트에 `--gate-only`(아무것도 옮기지 않고 진행 중 작업 게이트만 판정)를 추가해 feature 브랜치에서 먼저 돌린다. 판정 로직은 스크립트 한 벌뿐이다. 진짜 충돌(exit 4)은 최신 main과 비교해야 해서 사전 검사로 잡지 못하고, 기존 모드처럼 merge 뒤에 멈춘다.
- **확인은 1회, 1단계 전에만.** 커밋될 파일(untracked 별도 표시), 커밋 메시지 초안, 머지 방향, 로컬 main이 원격보다 뒤처졌는지(fetch 없이 판단)를 보여 준다. 이후 단계는 묻지 않는다.
- **이 모드만 커밋한다.** 1단계는 작업 트리 전체, 5단계는 고정 메시지 `chore(forge): integrate <branch> forge records`로 커밋한다. 기존 두 모드의 "통합을 커밋하지 않는다"는 그대로 유지한다.
- **push와 브랜치 삭제는 하지 않는다.** 이 리포에서 main push는 곧 배포이고, 배포 규칙은 push를 CHANGELOG와 버전 범프 뒤에 둔다.
- **실패하면 그 자리에서 멈추고 되돌리지 않는다.** 재실행하면 남은 단계부터 이어진다(변경 없으면 1단계 생략, 이미 머지됐으면 "Already up to date"). 3단계 충돌은 기존 동작대로 그대로 두고 멈추며 `git merge --abort`는 하지 않는다.
- **코어 스크립트는 여전히 git을 실행하지 않는다.** git 조작은 전부 스킬 계층의 일이다. CI는 영향을 받지 않는다(`--gate-only`를 주지 않으면 기존과 같다).

## 기각한 대안
- **현재 브랜치에 따라 `fg-merge <branch>`의 의미를 바꾸는 안.** 같은 명령이 서 있는 위치에 따라 반대로 동작해, 잘못 서 있으면 엉뚱한 방향으로 머지된다.
- **별도 스킬(`fg-ship` 등)을 만드는 안.** 통합 단계를 fg-merge와 공유해야 해서 경계가 겹친다.
- **게이트 조건을 스킬 산문에 적고 스킬이 직접 확인하는 안.** 게이트 정의가 두 벌이 되어 조용히 어긋난다.
- **게이트를 4단계에 그대로 두는 안.** merge 커밋이 이미 main에 들어간 뒤 멈추게 되어 `git reset`으로만 되돌릴 수 있다.
- **push나 브랜치 삭제까지 하는 안.** 확인 1회가 원격 게시까지 승인하는 셈이 되고 배포 규칙을 우회한다.
