# 플레이북은 기계 확인 가능한 두 종(bug-fix·refactor)만, eval 마커 형식을 일반화해 들인다

## Status
accepted

## 맥락
pstack(Lauren Tan, MIT)의 poteto-mode는 작업 유형을 보고 플레이북을 고르고, 그 단계를 할 일 목록에 그대로 복사하며, 생략할 때는 `skip: <reason>`을 남기게 한다(조용한 생략 금지). 이 개념을 forge에 적용하려는 요청에서 출발했다.

forge에는 이미 축소판이 있다. PLAN-FORMAT.md의 fix-forward eval 규칙은 계획의 **출처**(`generated-by`)를 보고 "영속 회귀 체크 슬라이스 + red→green DoD"를 요구하며, 생략은 `<!-- eval: none — <사유> -->`로만 허용한다(lint E6/E7). 측정된 구멍이 하나 있다 — 이 규칙은 `generated-by` 계획에만 걸리므로, 사용자가 fg-ask로 직접 가져온 버그 수정은 회귀 체크 의무를 지지 않는다. 같은 버그가 입구에 따라 다르게 다뤄진다.

## 결정
**계획 마커 `<!-- playbook: bug-fix|refactor -->`를 두고, 각 필수 단계를 `<!-- <단계>: S<n> -->` 또는 `<!-- <단계>: none — <사유> -->`로 표현해 plan-lint가 강제한다. 단일 정의는 PLAN-FORMAT.md의 새 절이다.**

- **bug-fix**: 기존 `eval` 마커를 그대로 재사용한다. `generated-by` 계약은 불변이고, `playbook: bug-fix`는 같은 요구가 걸리는 입구를 하나 더 연다.
- **refactor**: 새 `pin` 마커(구조 이동 전 동작을 고정하는 슬라이스). 여기에 더해 **다른 모든 슬라이스가 pin 슬라이스에 (직·간접) 의존**해야 한다 — "먼저 고정"이라는 순서를 산문이 아니라 구조로 강제한다.
- **선택**: fg-ask가 그릴링 중 판정하고 진행 중인 질문 안에 한 줄로 고지한다(별도 질문 없음, 사용자가 뒤집을 수 있음). 기본은 마커 없음. 계획당 플레이북 하나 — 섞인 작업은 계획을 나눈다(고정된 동작을 바꾸는 버그 수정은 pin을 깬다).

## 트레이드오프 / 결정 근거
- **두 종만인 이유 — lint가 강제할 수 있는 단계만.** 버그 수정의 red→green과 리팩터의 고정-후-이동은 언어 중립 마커와 의존 그래프로 검사된다. 기능(Feature)의 "데이터 모양을 먼저 이름 짓기" 같은 판단 단계는 lint로 강제할 수 없어 산문 규칙 하나를 더 늘릴 뿐이다.
- **새 문법 대신 eval 형식 일반화**: pstack의 `skip: <reason>`은 forge에 이미 `none — <사유>`로 존재한다. 사용자 언어로 단계 이름을 복사하는 방식은 lint가 읽을 수 없다.
- **fg-agenda의 "유형 분류 안 함"(ADR `260805-201313` 결정 6)과의 관계**: 그때 거부한 것은 의제 줄의 *해소기 종류*였고, 이것은 계획의 *필수 단계 계약*이다. 다만 분류 체계를 늘리는 데 대한 경계는 유효하므로, 대부분의 작업은 플레이북 없이 흐르게 했다.
- **알려진 한계**: fg-ask가 분류를 잊으면 마커가 없고 lint는 그것을 못 잡는다(사용자 언어 산문 판단). 리팩터·기능에서 단계 누락 사고는 측정되지 않았다 — refactor는 근거가 아니라 강제 가능성으로 골랐다.

## 고려한 대안
- **eval 규칙 범위만 넓히기(플레이북 개념 없음)** — 측정된 구멍만 막는 최소안. 거부: 리팩터의 동작 고정이라는 두 번째 기계 확인 가능 단계를 담을 자리가 없다.
- **pstack식 전면 도입(다수 플레이북 + 라우팅 + 미매칭 시 맞춤 설계)** — 거부: forge의 라우팅은 상태 기반(fg-next)이고, 강제 불가능한 산문 단계가 대부분이다.
- **단계 텍스트 복사 + `skip:` 줄** — 거부: lint 불가.
- **매 그릴링마다 플레이북 질문** — 거부: 모든 작업에 질문 1개를 더한다.
- **한 계획에 여러 플레이북** — 거부: pin과 버그 수정이 충돌한다.
- **보류** — 거부: 사용자가 도입을 원했고 측정된 구멍이 이미 있다.

## Consequences
- 봉인된 계획에 `playbook`·`pin` 마커가 영속적으로 남는다.
- plan-lint 트윈과 그 테스트·패리티 테스트가 확장된다.
- 개념 각색이며 코드 vendoring이 아니다.
