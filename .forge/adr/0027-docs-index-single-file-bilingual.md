# docs/index.html은 단일 파일 이중언어(인라인 + CSS 토글) — README의 두 파일 방식과 의도적으로 다름

랜딩 페이지 `docs/index.html`에 한/영을 함께 제공하면서, 이 프로젝트가 README(`README.md`/`README.ko.md`)에 쓰는 **두 파일 이중언어** 관례를 따르지 않고, **한 파일 안에 KO/EN 텍스트를 나란히 인라인**하고 `<html data-lang>` + CSS `display:none`으로 표시를 전환하기로 했다. 이유: (1) 요구사항이 "페이지 안 한영 전환 토글"이라 리로드 없이 스크롤을 유지하는 제자리 전환 UX가 자연스럽고, (2) 레이아웃·스타일·SVG·애니메이션이 언어 독립적이라 **구조는 한 벌만** 유지하면 되므로(텍스트만 두 벌) 두 파일 통째 sync보다 드리프트 표면이 작으며, (3) 텍스트에 `<code>`·`<br>`·인라인 스타일이 섞여 있어 JS i18n 딕셔너리(문자열 추출) 방식은 사전값에 HTML을 담아야 해 오히려 취약하기 때문이다. 빌드 시스템이 없다는 프로젝트 제약과도 맞는다(순수 vanilla JS 토글).

## Considered Options
- **두 파일(`index.html` + `en/index.html`)** — README 관례와 일치하고 SEO(별 URL)에 유리하나, 전환이 리로드+상단 점프이고 전체 페이지를 2벌 sync해야 해 드리프트 위험이 가장 큼. 기각.
- **단일 파일 + JS i18n 딕셔너리(`data-i18n`)** — 구조·텍스트 각 한 벌로 가장 DRY하나, 혼합 콘텐츠(code/br/span) 때문에 사전값에 마크업을 우겨넣어야 하고 키 누락 시 빈 텍스트가 노출되는 취약성. 기각.
- **(채택) 단일 파일 + 양 언어 인라인 + CSS 토글** — 제자리 전환 UX + 구조 한 벌 유지 + 혼합 콘텐츠에 강함. 비용은 텍스트 마크업 2벌(파일 ~47KB→~75KB)로, 정적 페이지에서 무시할 수준.

## Consequences
- KO만 고치고 EN을 빠뜨리는 드리프트를 막기 위해, CLAUDE.md의 "README 이중 언어 동기화" 규약을 `docs/index.html`의 KO/EN 동시 갱신까지 확장한다.
- 향후 이 페이지의 이중언어 관리 방식을 두 파일이나 JS 딕셔너리로 바꾸려면 재구조화가 필요하다(중간 정도의 되돌리기 비용).
