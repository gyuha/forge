# fg-run은 위험/큰 변경에 한해 워크플로우 안에서 코드 리뷰를 돈다

## Status
accepted

## 맥락과 결정
"워크플로우에 review를 넣을까? Dynamic Workflow에 이미 포함된 것 아닌가?"라는 물음에서 출발. 정정: ① fg-run은 **계획-검증**(각 슬라이스 완료 기준을 실제 산출물에 대고 확인, §3)을 *이미 항상* 한다. ② 그러나 **코드 품질 리뷰**(버그·보안·구조)는 없었다. ③ Dynamic Workflow는 리뷰를 자동 포함하지 않는다 — 오케스트레이션 스크립트에 넣은 단계만 돈다(adversarial-verify는 권장 *패턴*이지 자동 아님).

그래서 갭(계획대로 만들었나 ≠ 잘 만들었나)을 메우되 루프를 늘리지 않기로 한다:
- **새 루프 단계(fg-review)를 만들지 않는다.** 대신 **fg-run 워크플로우 안의 리뷰 단계**로 둔다(§3 확장). 4단계 루프 모양 보존.
- **위험/크기 게이트** — 변경이 위험 영역(인증·데이터·공개 API·마이그레이션)이거나 상당히 클 때만 리뷰 단계를 스크립트에 포함. 사소한 변경은 생략(매 변경 리뷰는 느리고 retro 비강제 원칙과도 충돌).
- **이식성** — 리뷰는 워크플로우 자신의 adversarial-verify 서브에이전트(코어 Agent/Workflow)로 구성하므로 외부 스킬 하드 의존 없음. code-review 역량이 가용하면 활용(선택).
- **findings 처리** — 실제 문제는 그 워크플로우 안에서 수정→재검증. 잔여 중대건은 `run.md`에 divergence로 기록해 fg-learn/재그릴링으로. 워크플로우는 실행 중 사람 입력을 못 받으므로 리뷰도 자동 수행되고 결과는 핸드오프에서 사람이 본다.

## 고려한 대안
- 새 루프 단계 fg-review(run과 learn 사이) — 거부: 4단계 루프·상태 계약·전 문서를 건드리는 큰 변경.
- 항상 리뷰 — 거부: 사소한 변경에도 비용, retro 비강제 원칙과 충돌.
- 추가 안 함(계획-검증으로 충분) — 거부: 위험 변경의 품질 갭이 남는다.
- 외부 code-review 스킬 하드 의존 — 거부: 이식성. 워크플로우 자체 서브에이전트로 충분, 외부는 선택적 보강.

## 관련
여기서 거부한 "선택적·심층 적대 리뷰"는 이후 **ADR-0018(fg-adversarial-review)**로 별도 도입됐다 — 루프 밖 선택 유틸리티로, 본 ADR의 자동 품질 리뷰(워크플로우 내부·게이트)와 **보완 관계**다(자세·범위·발동·위치가 다름). 둘은 공존하며 어느 쪽도 다른 쪽을 대체하지 않는다.
