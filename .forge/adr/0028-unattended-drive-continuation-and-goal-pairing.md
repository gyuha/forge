# 무인 주행 연속성 — 턴 내 계속 강제 + /goal 주경로 + 공유 DRIVE.md

## Status
accepted

## 맥락
`fg-next all`(과 자매 `fg-loop`)이 "다음 단계 하나만 하고 중단"된다는 사용자 피드백. 근본 원인은 버그가 아니라 구조다: 스킬은 모델에게 주는 마크다운 지시문일 뿐이고, "턴"은 모델이 도구 호출을 멈추면 끝난다. 멈춤 지점은 셋이다 — (1) **소프트 양보**: 위임된 fg-run/fg-done의 **진술형 핸드오프**(ADR-0015: "다음은 X — 멈춤")를 오케스트레이터가 턴 경계로 오인해 양보(가장 흔함), (2) **비동기 경계**: 백그라운드 Dynamic Workflow 실행, (3) **사람 경계**: 워크플로우 스크립트 승인. (2)(3), 그리고 (1)의 잔여는 **Stop hook(`/goal`) 없이는 구조적으로 넘을 수 없고, 스킬은 `/goal`을 스스로 걸 수 없다(사용자만 침)**.

두 개의 불균형도 있었다: fg-loop에는 이미 "턴 사이 멈추지 마라"·"reliably enforced only by /goal"라는 강한 서술이 있었으나 **fg-next all에는 그 강제 문장이 없었다**(사용자가 겪은 바로 그 갭). 그리고 `/goal` 페어링 서술이 두 스킬에 중복돼 드리프트 위험(CLAUDE.md "알려진 불일치" 목록이 이미 그런 드리프트의 증거).

## 결정
1. **턴 내 계속 강제(best-effort).** 오케스트레이터(all-mode/loop)는 위임 스킬의 진술형 정지를 **턴 경계로 보지 않고** 즉시 다음 단계를 도출(fg-status 상태 머신)·실행한다. 봉인은 정지점이 아니다. 반복-메뉴 버그(ADR-0015) 재발 없음 — 구동은 **변하는 상태**(봉인→다음 승격)로 전진하지, 불변 상태에서 루프하지 않는다.
2. **`/goal`을 무인 주행의 operating premise·붙여넣기 주경로로.** 진입 시 정확한 정지-조건이 담긴 `/goal` 한 줄을 **주경로**로 제시하고, 그 붙여넣기가 진입 확인(재실행 방지 게이트)을 겸한다("go"/직접 진행도 확인). 별도 이중 게이트 없음.
3. **공유분을 `skills/fg-next/DRIVE.md` 한 벌로 추출.** 턴 내 계속(Part 1) + `/goal` 페어링·문구 규칙·정직한 폴백(Part 2)을 담고 fg-next(all)·fg-loop이 함께 참조한다(FORGE-ROOT.md와 동형의 "단일 정의·복붙 금지"). **각 레인은 자기 벽 집합을 스스로 채운다** — DRIVE.md는 중립 메커니즘만, 벽 목록은 각 SKILL.md(fg-next all의 4벽 vs fg-loop의 goal-met·tension·safety 등).

## 고려한 대안
- **스킬이 settings.json에 지속 Stop hook 자동 설치(완전 자동 /goal)** — 기각. `/goal`은 세션 범위·자동 해제 hook이지만 settings.json hook은 **영속**이라 이후 모든 턴의 정지를 막고, 구동이 예기치 않게 죽으면 hook이 남아 "멈춤 불가" 상태를 만드는 큰 발모(정리 취약). 강력함보다 위험이 크다.
- **인라인 중복 유지(공유 추출 안 함)** — 기각. 두 스킬에 같은 /goal 서술이 갈라져 드리프트(이미 fg-loop이 fg-next 섹션을 참조하는 반쪽 결합 상태였음).
- **현행 유지** — 기각. 사용자의 실제 고통이고, fg-next all이 fg-loop보다 약한 비대칭이 결함이었다.

## 결과
- fg-next all이 fg-loop 수준의 턴 내 연속성을 확보한다 — 작은/직접 실행 작업 백로그는 `/goal` 없이도 한 턴에 끝까지 비워진다.
- **정직한 한계 명문화**: 턴 내 계속은 best-effort(텍스트가 모델의 양보를 100% 못 막음), `/goal`이 reliable한 크로스-턴 보장. 어느 쪽도 "절대 안 멈춤"을 주장하지 않는다.
- **불변**: ADR-0015(위임 스킬은 *사람* 호출 시 여전히 진술-후-정지 — 바뀐 건 오케스트레이터의 해석뿐). ADR-0009/0010/0016의 벽·검증 게이트 전부 불변. 자동 hook을 기각했으므로 스크립트 승인은 여전히 사람이 필요한 정지점.
- README·`docs/skills.md`가 `/goal` 메커니즘을 처음으로 사용자 문서에 명시한다("looped until it needs you" 약속의 실제 메커니즘 노출).
- 교차참조: [ADR-0010](0010-fg-next-all-momentum-mode.md)(all-mode 정의 정밀화)·[ADR-0016](0016-fg-loop-goal-driven-bounded-replan.md)(fg-loop 공유분 이관)·[ADR-0015](0015-fg-run-handoff-menu-others-stated.md)(진술형 핸드오프 = 소프트 양보 원인, 불변)·[ADR-0011](0011-branch-isolated-forge-root.md)(FORGE-ROOT.md 공유문서 선례)·[ADR-0009](0009-verification-gate-before-seal.md)(검증 게이트 불변).

## 개정 2026-08-22 — forge가 자기 Stop hook을 배포한다 (기각 재검토)

**이 개정은 위 「고려한 대안」의 첫 항목을 뒤집는다.** 그 항목은 이렇게 기각했다 — *"스킬이 settings.json에 지속 Stop hook 자동 설치(완전 자동 /goal) — 기각. settings.json hook은 **영속**이라 이후 모든 턴의 정지를 막고, 구동이 예기치 않게 죽으면 hook이 남아 '멈춤 불가' 상태를 만드는 큰 발모(정리 취약)."* 사용자 피드백이 다시 왔고(`/fg-next all`만으로는 한 사이클 후 멈춘다), 확인해 보니 **기각 사유 세 개가 이 설계에서는 각각 성립하지 않는다.**

| 원 기각 사유 | 왜 더는 성립하지 않나 |
| --- | --- |
| "스킬이 **settings.json**에 자동 설치" | 사용자 설정을 건드리지 않는다. **플러그인이 자기 `hooks/hooks.json`으로 배포**하며, 이는 공식 훅 문서가 명시하는 위치이고(사용자·프로젝트 훅과 병합) forge는 이미 같은 경로로 `SessionStart`를 배포해 왔다 — 새 메커니즘이 아니라 **검증된 경로의 두 번째 사용**이다. |
| "**영속**이라 이후 모든 턴의 정지를 막는다" | 훅 등록은 영속이지만 **효과는 마커 조건부**다. `<forge-root>/drive.md`가 없으면 exit 0이므로 주행하지 않는 세션·주행하지 않는 사용자는 완전히 무영향이다. 기각문이 두려워한 것은 *무조건* 막는 훅이었다. |
| "죽으면 hook이 남아 **멈춤 불가**" | 이번에 확인된 사실이 이 위험을 키우는 동시에 해법을 강제했다 — **하네스는 Stop hook에 루프 보호를 전혀 제공하지 않는다**(`stop_hook_active` 류 입력 필드가 없다). 그래서 시간 상한(30분)과 반복 상한(50회 차단)을 forge가 직접 진다. 둘은 **서로 다른 실패를 막는다**: 세션이 주행 중 죽어 남은 마커는 시간 상한만, 같은 단계를 재도출하는 주행은 반복 상한만 끊는다. |

**확인된 외부 사실**(공식 훅 문서, 2026-08-22): `Stop`·`SubagentStop` 이벤트 존재 · **Stop에서 `exit 2`가 정지를 막고 대화를 계속시킨다**(차단 메시지는 훅의 stderr) · **exit 0=진행, exit 1=비차단 오류로 역시 진행**, 2=차단 · **플러그인 `hooks/hooks.json`이 Stop hook을 제공할 수 있다** · **루프 보호 필드 없음** · 훅 입력에 `session_id` 포함.

**결정**
1. **forge가 `Stop` hook을 배포한다** — `hooks/hooks.json`에 검증된 `SessionStart` 항목과 구조적으로 동일한 항목을 두고, 본체는 결정론 트윈 `scripts/forge-hook-stop.sh`/`.js`(ADR-0022)다.
2. **훅은 벽을 판정하지 않는다.** 주행이 종료 상태·벽에서 `drive.md`를 **삭제**하는 것이 "멈춰도 된다"의 표현이다. 훅은 "마커 있나 · 상한 안인가 · 내 세션인가"만 본다. 리포에서 가장 위험한 물건이므로 `.forge/` 상태 머신을 복제하지 않는 단순함 자체가 안전 장치다.
3. **모든 실패·모호 경로는 정지를 허용한다.** 마커 없음·상한 초과·세션 불일치·파싱 불가·카운터 쓰기 실패·시계 없음·forge 프로젝트 아님 → 전부 exit 0. 하네스의 exit 1도 진행이므로 스크립트가 죽어도 세션이 갇히지 않는다.
4. **동의는 `all`/`fg-loop` 호출 자체다** — 새 config 키도 새 토글 스킬도 만들지 않는다. `DRIVE.md`는 `all`을 이미 「벽까지 주행」으로 정의했고, 한 사이클 정지는 의도가 아니라 못 지킨 약속이었다. 별도 토글은 의도 복원에 통행료를 받는 셈이다.
5. **`/goal`은 폐기되지 않고 폴백으로 남는다** — 훅이 걸리지 않는 정황(구버전 하네스·플러그인 비활성·훅 로드 전 세션)에서 유일한 수단이고, 3번의 안전 설계상 "훅이 안 걸림"은 조용히 일어날 수 있다.

**결과**
- 위 결정 2 「`/goal`을 operating premise·주경로로」는 **주경로가 훅으로 이동**하는 형태로 개정된다(배선과 문서 반영은 part 2 소관).
- 훅은 **세션 시작 시 로드**되므로 배포한 세션에서는 절대 발동하지 않는다 — `.claude/agents/` 카드와 동형의 제약(ADR-0024). 그래서 이 작업은 두 part로 쪼개졌고 part 1은 **동작 무변화(no-op)**로 출하된다(마커를 쓰는 주체가 아직 없다).
- **정직한 한계**: 상한 숫자(30분·50회)는 원리에서 도출된 값이 아니라 고른 값이다. 관측이 쌓이면 조정한다.
- **불변**: ADR-0009의 검증 게이트, ADR-0010/0016의 벽 집합, ADR-0015의 진술형 핸드오프. 훅의 stderr는 사용자에게 내는 핸드오프가 아니라 에이전트에게 가는 계속 신호다.

## 개정 2026-08-22 (2) — 주경로가 `/goal`에서 forge의 Stop hook으로 이동

위 결정 2는 *"`/goal`을 무인 주행의 operating premise·붙여넣기 주경로로"* 였다. 같은 날 첫 개정이 forge가 자기 Stop hook을 배포하기로 정했으므로, **주경로는 훅이고 `/goal`은 폴백**이다. 배선의 형태는 이 개정이 정한다.

**결정**
1. **두 차선이 진입 시 `<forge-root>/drive.md`를 쓰고 모든 출구에서 지운다.** fg-next `all`은 네 벽 + 종료 상태 + 사람이 물리적으로 필요한 지점(스크립트 승인), fg-loop은 아홉 벽 + goal-met + `waiting` 턴 종료. **`waiting`이 특히 놓치기 쉽다** — 벽이 아니지만(§4) 외부 증거가 오기 전에는 진행할 수 없으므로 마커가 살아 있으면 아무 지역 행동으로도 바뀌지 않는 것에 대고 턴이 헛돈다.
2. **마커는 별 파일이며 `loop.md`에 필드를 추가하지 않는다.** fg-loop이 `waiting`을 최상위 필드 대신 기존 원장에 흡수한 결의를 깨지 않기 위함이고, 덤으로 훅이 파일 하나만 읽는다.
3. **`/goal` 붙여넣기 라인은 조건부로만 제시한다** — 훅이 살아 있지 않다고 볼 이유가 있을 때(이 세션에서 forge를 막 설치·갱신했을 때가 가장 구체적이다). 훅이 일하는 상황에서 매번 출력하면 소음이다. 반면 훅의 부재는 **설계상 조용하므로**(세션 시작 로드·플러그인 비활성·구버전 하네스) 폴백 서술 자체는 지우지 않는다.
4. **`fg-doctor`가 낡은 마커를 경고한다(A9).** 30분 상한을 넘긴 마커는 아무것도 막지 않지만 "어떤 주행이 정리하지 않고 나갔다"는 뜻이므로 보고한다. 읽기 전용 — 자동 삭제하지 않는다.

**결과**
- `/fg-next all` 또는 `/fg-loop` **한 번**으로 run → learn(자동 skip) → done이 백로그가 빌 때까지 이어진다. 사용자 요구였던 *"`/goal` 없이 forge 기능만으로"* 가 이로써 성립한다.
- **`DRIVE.md` Part 2가 정본**이며 두 차선은 마커 형태·삭제 지점만 자기 SKILL.md에 담는다(단일 정의·복붙 금지 유지).
- **정직한 한계**: 훅은 세션 시작 시 로드되므로 **배포한 세션에서는 발동하지 않는다**. 그래서 part 1(메커니즘)과 part 2(배선)를 쪼갰고, part 2의 실제 무인 주행 UAT는 재시작된 세션에서만 관측된다.
