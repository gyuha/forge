# 2026-08-05 — fg-visual: 확정 클릭이 에이전트를 깨운다 (Monitor 감시 + 필수 확정 버튼)

## 계획 대비 실제

**DoD 두 층 모두 충족했다.** 1층(작성 완료): `VISUAL.md` 313→371줄에 7지점, `SKILL.md` 50→53줄, 새 ADR `260805-005436`, `CONTEXT.md` `Visual Companion` 정정, 소비자 문서 4곳. 2층(실 동작 검증): S6 dogfood가 세 확인을 각각 이벤트로 입증했다. vendored 5파일은 전 과정 0줄 변경, fg-doctor 최종 0 errors / 0 warnings.

**S6의 핵심 증거는 같은 사용자 행동의 대비다.** 베타 클릭이 파일에 기록됐는데 알림은 오지 않고, 1.1초 뒤 확정만 통과해 알림이 왔다. 필터가 소음을 걷어내면서도 클릭 패턴 정보(`VISUAL.md`가 값있다고 적은 것)를 버리지 않는다는 뜻이다 — 깨어난 뒤 파일 전체를 읽으면 탐색 경로가 그대로 보인다.

**발산 6건 중 in-run 수정이 3건**이라 divergence가 높다. 그중 두 건은 계획이 예측하지 못한 구멍이었고, 한 건은 완료 기준의 헐거움이었다.

## 학습

**1. 이벤트를 하나 받는 설계는 그 이벤트가 *여러 번* 올 때를 반드시 정의해야 한다.** 이번의 가장 큰 구멍이다. 그릴링에서 "정착 식별"을 확정 버튼으로 풀 때 *한 번의* 확정만 상정했고, 다중 확정은 논의조차 되지 않았다. 실주행에서 성격이 **반대인** 두 동작이 같은 흐름에 나타났다 — 더블클릭이 같은 값을 798ms 간격으로 보내 한 결정에 두 번 깨우는 **소음**, 그리고 확정 후 마음을 바꿔 다른 값으로 다시 확정하는 **기능**(`confirm:gamma` → 탐색 → 10초 후 `confirm:beta`).

그래서 직관적 처방인 **"버튼 비활성화"가 오답이었다** — 소음을 막으면서 정당한 변심을 함께 죽인다. 두 층으로 갈라야 풀린다: 버튼의 `dataset.sent` 가드가 *같은 선택의* 재전송만 떨어내고, 에이전트 측이 "마지막 confirm을 답으로 삼고 이미 처리한 것과 같으면 다시 답하지 않는다"로 멱등을 보장한다. 빠른 더블클릭이 가드를 앞지를 수 있으므로 한 층으로는 부족하다.

**같은 구멍이 `ask-input`에 이미 있음을 확인했다**(추정이 아니라 스니펫을 읽어 확인 — `textContent='Sent'`만 있고 재전송 가드 0). 즉 이건 확정 버튼 하나의 실수가 아니라 **이 파일의 전송 위젯 계열이 공유하는 설계 누락**이다. 계획이 "ask-input의 형태 변경"을 비목표로 뒀으므로 이번엔 안 고치고 후속으로 남겼다.

**다음에 다르게: 사용자 조작을 이벤트로 받는 위젯을 설계할 때 "두 번 눌리면?"을 그릴링에서 반드시 묻는다.** 한 번의 성공 경로만 그리면 그 설계는 실주행 30초 안에 구멍이 드러난다.

**2. 완료 기준이 경고를 통과시켰다 — `0 errors`가 아니라 `0 errors 0 warnings`여야 했다.** S2가 새 능력을 한 절 추가하며 `description`이 556 → 615 코드포인트가 되어 `DESC_MAX=600`을 넘겼다. HEAD 시점엔 임계값 아래였으니 이번 작업이 만든 회귀다. 그런데 S2의 완료 기준은 산문("한 문장 이상 길어지지 않았으며 트리거 문구 보존")이라 충족했고, 기계 검사를 담은 S5의 기준은 **"fg-doctor가 0 errors"**여서 warning인 B16을 그냥 통과시켰다. 결국 S5 에이전트가 자기 범위 밖이라며 보고해준 덕에 알았다 — 기준이 잡은 게 아니다.

**다음에 다르게: 기계 린트가 이미 있는 영역을 고치는 슬라이스는 완료 기준에 그 린트의 *전체* 통과를 넣는다.** forge에서는 `fg-doctor`의 errors만이 아니라 warnings까지다. warning을 "나중에"로 남기면 우리가 만든 드리프트를 우리 기준이 승인한다.

부수적으로, **B16이 정확히 이 부류를 위해 존재한다는 것이 실증됐다.** ADR `260716-22a`가 "description은 트리거 코어로 간결하게"를 결정하고 fg-doctor가 드리프트를 린트로 걸어 뒀는데, 새 능력이 들어올 때마다 description이 자라는 것이 실제 압력이었다. 트리거 문구 6개와 새 절을 모두 지킨 채 문장 두 개를 압축해 임계값 아래로 되돌렸다.

**3. `replace_all`을 믿지 말고 개수로 검증한다.** 확정 버튼 스니펫이 `VISUAL.md`에 두 군데 있었는데(최소 예제 + 정본 절), `replace_all: true`로 가드를 넣었더니 **정본 절만 바뀌고 최소 예제는 그대로였다** — 두 스니펫의 들여쓰기·형태가 미묘하게 달랐기 때문이다. `grep -c 'dataset.sent'`가 기대치(5)보다 적은 3을 반환해서 잡았다. 최소 예제를 복붙하는 사람이 구멍 있는 버튼을 만들 상태로 남았을 것이다.

**다음에 다르게: 같은 스니펫이 문서에 2곳 이상 있으면 수정 후 등장 횟수를 세어 확인한다.** 정본이 하나뿐이라고 가정하지 않는다 — 문서는 예제를 반복한다.

**4. 도메인 에이전트가 실제로 값을 냈다 (ADR-0024 경로의 첫 활용).** `skill-author`에 S1·S2, `manifest-doc-syncer`에 S5를 위임했다. 적합도가 좋았다 — `skill-author`는 forge 컨벤션(Mermaid 금지, 영문 본문 + 한국어 UI 문자열, 단일 정의라 `VISUAL.md`의 절차를 `SKILL.md`에 복제하지 않기)을 프롬프트에서 따로 강조하지 않은 부분까지 지켰고, `manifest-doc-syncer`는 README 이중언어 1:1 대응을 **스스로 검증해 보고**했다. 카드에 `model:`이 없어 eco 캡(sonnet)이 적용됐고 품질 문제는 없었다.

주의로 남길 것: **에이전트가 자기 범위를 정확히 지킨 대가로, 범위 밖 문제를 "보고만" 한다.** B16 경고가 그랬다 — `manifest-doc-syncer`가 발견했지만 자기 파일이 아니라 고치지 않고 보고했고, 오케스트레이터가 받아 처리해야 했다. 위임할 때 범위를 좁게 주는 것은 옳지만, **보고된 범위 밖 항목을 오케스트레이터가 반드시 소비해야** 그 정직함이 값이 된다.

**5. 이번 변경이 유휴 타임아웃 함정의 빈도를 올린다.** visual 서버의 4시간 유휴 타임아웃은 *인증된 요청*만 활동으로 세므로 에이전트가 화면을 밀어둔 것은 활동이 아니다. 사용자가 5시간 11분 뒤에 열려 하자 이미 자기 종료해 있었다("url이 열리지 않음"). vendored 서버의 기존 성질이고 버그가 아니지만 — **종전에는 답을 주려면 곧 터미널에 뭘 보내야 했으므로 방치 구간이 짧았는데, 이제 "클릭만 기다리는" 상태가 정상 흐름이 되어 아무 요청 없이 시간이 흐르기 쉽다.** 이 결정의 직접적 결과라 ADR Consequences에 적었다.

**6. 세션 재장전 규칙이 문서상 규칙이 아니라 실제로 두 번 발동했다.** 서버가 죽고 새 세션 디렉터리가 생기면 감시는 **죽은 세션의 events를 tail**한다. S1이 Lifecycle에 넣은 "재시작 시 재장전"을 이번 실행에서 두 번(`bb9yamyqk` 정지 → `bbcsgovtd` 재장전) 밟았다. 규칙을 쓴 사람이 같은 세션에서 그 규칙의 필요를 겪은 셈이다.

## 후속 작업 후보

- **`ask-input` 전송 버튼에 같은 재전송 가드를 넣는다** — 학습 1에서 확인된 동일 결함. 확정 버튼과 같은 2줄(`dataset.sent`)이면 되고, `field`별로 키를 나누면 한 화면의 여러 입력도 구분된다. 이번 비목표였을 뿐 성격은 같다.
- **세션 재시작 후 `/forge:fg-visual` 1회 실행** — 편집한 `VISUAL.md`/`SKILL.md`를 스킬이 스스로 따르는지의 검증(DoD 2층의 나머지 절반). ADR-0024의 세션 로드 제약 때문에 이 작업에서는 원리적으로 불가능했다.
- **fg-ask 그릴링 경로에서의 체감 확인** — 결정 4가 범위를 "모든 경로"로 정했지만 검증은 fg-visual 단독뿐이다. 연달린 시각 질문에서 왕복 절감이 실감되는지, 확정 후 다음 질문이 너무 빨리 오지 않는지는 다음 웹 UI 작업의 실제 fg-ask 세션에서 드러난다.
- **미밟힌 분기 셋** — `confirm:none`(아무것도 안 고르고 확정), 다중 선택에서 `confirm:a,b` 형태, `Monitor` 부재 시 graceful 폴백.
