# 2026-08-10 — fg-loop에 `waiting`(외부 증거 대기)·`blocked-health`(능력 사전점검) 도입 (LoopX 개념 각색)

## 계획 대 실제
- 계획대로 된 것: 산출물 전부 — fg-loop `evidence: external` 선언·원장 `waiting ×N`·벽 2종(`stalled-waiting`·`blocked-health`)·능력 사전점검, fg-status 비-벽 구분 보고, ADR-0016 개정(quota 기각 이유 정확화 포함), 문서 4곳 동기. DoD (a)~(e) grep 전부 통과. Non-goals(quota/스케줄링/술어/`state:` 필드/claim-lease) 전부 지켜짐.
- Divergences: ① 실행 형태 — Dynamic Workflow 대신 직접 실행(슬라이스 직렬 의존, 사전 합의). ② **plan 설계 정정 1건** — 그릴링이 채택한 "최상위 `waiting:` 필드 신설"이 착수 직전 회고 읽기에서 두 번 적용된 규율("새 필드 대신 기존 절 흡수 → 소비자 ripple 회피", 2026-07-16·2026-06-12 회고)과 정면 충돌 → 승인받아 원장 흡수형으로 정정. ③ **Codex 적대 리뷰 high 1건** — stale `wall:`(재개·대기 전환 시 이전 벽 원인 미해제 → fg-status가 같은 상태를 "해결할 벽"과 "할 일 없는 대기"로 동시 보고) → `wall: none` 전이 규칙 3겹(resume 리셋·waiting 직전 확인·문구 정정+회귀 시나리오 예시)으로 수정. ④ 사소 — plan의 ADR 링크 2건이 실제 파일명과 불일치(그릴링 때 기억으로 적고 검증 안 함).

## 학습
- 다음에 다르게: **fg-ask 그릴링은 설계 결정(특히 상태 파일에 필드·상태를 더하는 결정) 시점에 같은 영역 회고의 "다음에 다르게"를 다시 대조해야 한다.** 이번 그릴링은 시작 전 회고 읽기는 통과했지만 Q6(필드 형태) 결정 때 그 선례를 못 꺼냈고, fg-run의 착수 전 회고 읽기가 뒤늦게 잡았다 — 잡혀서 다행이지 fg-run 규정이 없었으면 ripple 비용을 그대로 지불했다. 1회 사례라 규정 변경은 보류; 재발 시 fg-ask에 "설계 결정 시점 회고 재대조"를 명시하는 승급 후보.
- 다음에 다르게: **상태 enum에 새 값·새 비-정지 상태를 더할 때는 기존 값들의 전이 — 특히 해제(clear) 시점 — 가 명시돼 있는지 함께 감사하라.** stale `wall:` 결함은 새 코드의 버그가 아니라, 기존에 무해했던 암묵 규칙(재개 시 벽 해제 미명시)이 `waiting`(벽 아닌 턴 종료) 신설로 실제 오보고 경로가 된 것. 적대 리뷰가 정확히 이 부류(추가된 상태와 기존 상태의 상호작용)를 잡았다 — 상태 계약을 건드는 작업엔 봉인 전 적대 리뷰가 값을 했다.
- 재확인(3회+ 반복 패턴): forge-meta 지시문 작업의 UAT는 "관측 가능한 문서 구조(grep DoD)"까지만이고, 진짜 효과(외부 증거 대기가 실주행에서 벽으로 오분류되지 않는가)는 실제 goal loop 주행에서만 드러난다.
- 사소: 그릴링이 plan에 ADR 파일명을 적을 땐 `ls`로 실명 확인 후 적을 것(이번 2건 불일치).
