# 2026-07-03 — statusline 단계 오표시 수정 (GitHub 이슈 #3)

## Plan vs actual
- What went as planned: S1~S5 전부 계획대로 완료. 스크립트 트윈(sh+js) 게이팅 규칙 반전 + `ask.md` 마커 신규 분기, 테스트 3파일 전부 green, 영속 문서 4종·스킬 문서 3종 동기, 설치본 동기화까지 계획이 정의한 12개 파일 범위와 정확히 일치(범위 이탈 없음, non-goals 불변).
- Divergences (낮음 — 재그릴링 불필요):
  - **계획 문구가 사실과 달라 서브에이전트(S3)가 코드 대조로 스스로 정정했다.** 계획은 "fg-ask가 fg-quick 이탈 시 ask.md를 삭제한다"는 트리거를 언급했지만, 실제로는 fg-quick→fg-ask 방향의 이탈 경로만 존재하고 역방향은 없다. S3가 이를 fg-quick SKILL.md·ADR-0003 대조로 발견해 존재하지 않는 트리거를 문서화하지 않고 실제 트리거(Output 시 삭제, 재시작 시 덮어쓰기)만 기록했다.
  - **S2가 계획에 명시된 것보다 넓은 범위의 기존 테스트를 고쳐야 했다.** "plan-only 기대값 수정" 한 줄이었지만 실제로는 같은 fixture를 재사용해 다른 것(브랜치 해석·stdin cwd 파싱)을 검증하던 케이스가 10개 있었다. 계획 단계에서 관련 회고 2건의 교훈을 미리 슬라이스 브리핑에 반영해둔 덕에(아래 참고) 서브에이전트가 정확히 찾아냈다.
  - **fg-ask 그릴링 중 사용자 무응답으로 채택한 미확정 가정 3개(범위/메커니즘/청소 방식)가 실행 결과 전부 무리 없이 들어맞았다.**

## Learnings
- Do differently next time: 없음 — 이번엔 오히려 "다르게" 할 게 아니라 **이미 하고 있던 걸 계속하라**는 확인에 가깝다.
- Confirmed (계속 유지할 것):
  - **"출력 포맷 assert하는 테스트 파일 전부 grep" 교훈이 이번이 3번째 반복 등장인데, 이번엔 실제로 통했다.** 직전 두 회고(2026-06-XX, 2026-07-02 fg-statusline 작업 2건)에서 "계획에 명시된 파일만 고치고 넘어갔다가 다른 파일에서 놓칠 뻔했다"는 패턴이 반복됐었다. 이번엔 fg-ask 그릴링 시점에 계획(S2 슬라이스)에 "grep으로 특정한 3개 테스트 파일"을 미리 못박아뒀고, 그 결과 S2가 숨어 있던 10개 케이스를 전부 찾아 고쳤다(실제로 놓친 게 하나도 없음). **결론: 이 교훈은 이제 "그릴링 시점에 영향받는 출력-포맷-assert 파일을 미리 grep해 계획에 못박는다"는 구체적 실행 방법으로 굳어졌고, 이번 검증으로 효과가 확인됐다.** 4번째도 같은 패턴이 나오면 그때는 정말 PLAN-FORMAT.md나 유사 문서에 정식 체크리스트 항목으로 승급할 후보(이번엔 ADR/CONTEXT 승급 바를 넘지 않아 보류).
  - **계획 문구와 실제 코드가 어긋날 때, 서브에이전트가 계획을 맹종하지 않고 코드를 대조해 정정한 판단이 옳았다.** fg-ask 그릴링이 만든 plan.md는 사람의 추측을 담을 수 있고, 실행 단계(fg-run 워크플로우)에서 코드베이스 자체가 최종 근거라는 원칙이 이번에 잘 작동했다.
